# 文档状态标注规范

本文档用于统一 `docs/` 中各类文档的状态标注方式，减少“文档还在，但已经不是当前依据”的歧义。

## 1. 适用范围

以下文档建议在标题下方增加状态说明：

- 路线图
- 阶段计划
- 迁移计划
- 问题分析
- 需求记录
- 设计方案
- 参考文档

长期稳定且明显属于规范类的文档，可以不强制逐篇标注；但如果存在历史版本并存，仍建议补状态。

## 2. 推荐状态

推荐使用以下几类状态：

- `状态：现行规范`
- `状态：现行参考文档`
- `状态：进行中计划`
- `状态：阶段计划，部分已落地`
- `状态：未完成阶段计划`
- `状态：历史阶段文档`
- `状态：历史契约草案`
- `状态：历史问题分析`
- `状态：需求/接口变更记录`
- `状态：历史讨论记录`

## 3. 推荐写法

推荐放在一级标题下方，使用两行以内说明：

```md
> 状态：阶段计划，部分已落地。
> 当前实际进展请优先查看 `docs/progress/...`
```

要求：

- 第一行明确状态
- 第二行只写最关键的阅读指引
- 不要写成长段说明

## 4. 目录与状态的关系

目录只表达“用途分类”，不自动等于文档状态。

例如：

- `docs/governance/` 下也可能有历史规范
- `docs/roadmaps/` 下可能同时存在进行中计划和已完成计划
- `docs/issues/` 下可能既有仍有效的需求记录，也有纯历史问题分析

因此，目录分层和状态标注必须同时存在。

## 5. 新文档创建规则

新增文档时：

1. 先决定目录归属
2. 再补状态标注
3. 如果文档会在后续失效，提前写明“现行依据在哪里”

最低要求：

- `roadmaps/` 新文档必须有状态
- `issues/` 新文档必须说明它是需求记录还是历史问题
- 涉及迁移、兼容、草案、阶段任务的文档必须有状态

## 6. 状态变更规则

文档状态发生变化时，应同步更新文档顶部说明。

典型触发点：

- 计划落地后，从“进行中计划”改为“阶段计划，部分已落地”或“历史阶段文档”
- 正式接口上线后，契约草案改为“历史契约草案”
- 需求落地后，issue 文档补充“仅作变更记录”
- 规范失效后，迁移到 archive 或改为历史说明

## 7. Review 检查点

评审文档类改动时，至少检查：

- 目录是否放对
- 是否补了状态说明
- 是否说明当前应以哪份文档为准
- 是否仍在引用已归档或已失效的路径
