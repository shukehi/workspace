# 边开发边生产使用安全约束（2026-03-13）

> 用途：为“系统仍在持续开发，但已经承载真实业务数据和日常使用”的阶段提供最小生产安全规则，降低发布、改库、配置变更和临时试验带来的事故风险。

## 1. 适用阶段

本文件适用于以下场景：

1. 系统仍在持续开发
2. 需求和实现还会继续调整
3. 但系统已经承载真实业务数据
4. 改动一旦出错，会直接影响日常使用

当前阶段的核心目标不是“最快改完”，而是：

1. 持续交付
2. 尽量不打断现有使用
3. 避免真实数据损坏
4. 保持可回退

## 2. 变更分级

### 2.1 低风险变更

可以按常规流程上线，但仍需最小验证：

1. 纯前端样式调整
2. 不改数据结构的页面交互优化
3. 只读查询逻辑优化
4. 文档与治理规则更新
5. 不影响数据写入语义的提示文案调整

### 2.2 中风险变更

上线前必须做定向验证：

1. 新增写接口
2. 修改已有表单提交流程
3. 修改库存、订单、配方等核心领域写入逻辑
4. 新增配置项
5. 调整导入导出逻辑

### 2.3 高风险变更

未经备份、验证和明确回退方案，不应直接上线：

1. 任何 schema / migration 变更
2. 任何字段语义变化
3. 任何配置文件结构变化
4. 订单、库存、配方、mapping、materials 的核心写路径调整
5. 会影响历史数据读取方式的重构

## 3. 上线前最小检查

任何中高风险变更在上线前至少完成：

1. 明确这次影响哪些模块
2. 明确是否影响真实数据写入
3. 备份 SQLite 与 `data/config/`
4. 明确回退方式
5. 手工验证关键链路

最小备份范围：

1. `data/runtime/database.sqlite`
2. `data/config/`

如果涉及公式导出或其他运行时产物，也应确认：

1. `data/runtime/color-formulas.exported.json`

## 4. 生产环境改库规则

生产环境默认只允许 additive change：

1. 新增表
2. 新增字段
3. 新增索引
4. 为新增字段提供默认值
5. 必要时对新字段做回填

生产环境默认不直接做：

1. 删除字段
2. 重命名字段但不做兼容
3. 重建表
4. 直接清空或替换数据库文件
5. 无验证地覆盖 `data/config/*.json` 结构

原则：

1. 先兼容，后清理
2. 先双读/兼容读，后退旧字段
3. 先保数据，再追求结构整洁

## 5. 发布时的最小手工验证

上线前后至少验证以下链路：

1. 订单读取
2. 订单写入或更新
3. 入库写入与回显
4. 配方读取与发布
5. materials / mappings 配置读取与保存
6. 关键页面是否还能打开历史数据

如果本次只影响局部模块，也不能跳过对应领域的关键写路径验证。

## 6. 回退规则

任何中高风险变更都应先想清楚“怎么撤回”。

最小回退思路：

1. 代码问题：
   回退到上一个稳定提交
2. 配置问题：
   恢复 `data/config/` 备份
3. 数据结构问题：
   优先停止继续写入，再决定是否恢复数据库备份

注意：

1. 不要在问题未定位时继续写生产数据
2. 不要一边排查一边继续做破坏性改库
3. 不要把“重新初始化数据库”当成默认回退方案

## 7. 当前阶段的工程约束

在“边开发边生产使用”的阶段，默认继续遵守：

1. 不推动后端全量 TypeScript 迁移
2. 高变化区域优先低摩擦实现
3. 稳定边界再做类型化和收敛
4. compatibility shell 不承载新逻辑
5. 新增高风险写接口优先补 validation

目标是避免同时叠加：

1. 业务变更风险
2. 数据迁移风险
3. 架构重写风险

## 8. AI 协作默认规则

后续如果由 AI 参与生产相关改动，默认应：

1. 先读取本文件和数据安全文档
2. 如果涉及数据或 schema 风险，先提示风险
3. 未经明确要求，不做破坏性 migration
4. 未经明确要求，不以“结构统一”为理由推动高风险重构
5. 修改后说明影响范围、验证点和回退要点

## 9. 当前阶段最重要的原则

1. 真实数据优先于结构洁癖
2. 可回退优先于一次到位
3. 小步发布优先于大改动合并
4. 已在使用的链路，先保稳定再谈重构
