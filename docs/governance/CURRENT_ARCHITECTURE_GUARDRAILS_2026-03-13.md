# 当前架构护栏（2026-03-13）

> 用途：记录当前项目在“边开发边使用、业务思路仍会频繁调整”阶段的工程边界，避免后续开发为了结构统一而过早引入高成本改造。

## 1. 当前阶段判断

项目目前处于：

1. 持续使用中的本地业务工具
2. 需求、数据结构、交互细节仍在快速迭代
3. 已开始做模块边界治理，但还不适合追求一次性定型

因此当前阶段的首要目标不是“全仓统一”，而是：

1. 保证可持续迭代
2. 保证已有真实数据不被轻易破坏
3. 逐步收敛稳定边界

## 2. TypeScript 策略

当前默认策略：

1. 前端 `src/` 继续保持 TypeScript 主体
2. 后端 `server/` 不做全量 TypeScript 迁移
3. 只在“稳定边界”和“纯逻辑模块”中优先引入 TypeScript

优先适合类型化的区域：

1. shared contracts / DTO
2. validators
3. policy / mapper / normalizer
4. 纯函数规则层

暂不优先类型化的区域：

1. `server/index.js`
2. 运行时脚本
3. migration 脚本
4. compatibility shell
5. 仍在频繁变化的后端主编排流程

原则：

1. 类型系统要服务于迭代速度
2. 不为“扩展名统一”牺牲当前开发效率

## 3. 后端演进策略

当前后端优先做的是边界治理，而不是语法层统一。

优先级顺序：

1. 先明确 controller / validator / service / repository 边界
2. 先抽离共享规则和纯逻辑
3. 先保留 compatibility shell，避免迁移期引用大爆炸
4. 后续再视稳定度推进 TypeScript

默认约束：

1. 新逻辑不继续堆进 legacy 兼容壳
2. compatibility shell 只允许转发，不承载新业务
3. 新增高风险写接口时，应优先补 request validation

## 4. 数据与 schema 演进策略

当前 schema 调整默认采用 additive 策略：

1. 先加字段、加表、加索引
2. 先兼容读旧数据
3. 先保留旧字段一段时间
4. 等业务语义稳定后再考虑清理历史结构

明确不鼓励的做法：

1. 为了“看起来更干净”而直接删旧字段
2. 在没有真实数据回归的情况下重建表
3. 在需求尚未稳定时一次性做大规模 schema 改造

## 5. 文档策略

当前阶段需要文档，但文档应短、小、可直接执行。

优先维护的文档类型：

1. 数据安全与备份规则
2. 当前架构护栏
3. 兼容层退场计划
4. 正在执行的重构路线图

不要求当前阶段维护的内容：

1. 过度理想化的长期架构蓝图
2. 与现状脱节的“大而全”设计说明

原则：

1. 文档要帮助后续开发少踩坑
2. 文档要能被 AI 和人直接读取后执行

## 6. AI 协作默认规则

后续如果由 AI 参与开发，默认先遵守以下护栏：

1. 先读取当前治理文档，再做高风险修改
2. 未经明确要求，不推动全量 TS 迁移
3. 未经明确要求，不做破坏性 schema 变更
4. 若发现某处仍在高频变化，应优先保留低摩擦实现
5. 若某处已经稳定，再建议做类型化、模块收敛和命名清理

## 7. 何时调整这份护栏

当出现以下信号时，可以提高“收敛强度”：

1. 核心业务对象连续 1 到 2 个迭代未发生结构性变化
2. 关键页面和 API 契约开始稳定
3. 本地真实数据已经积累到不允许频繁返工 schema 的程度
4. 当前主要痛点从“快速试验”转为“维护和重构成本过高”

在这些信号出现前，当前仓库默认采用：

1. 小步演进
2. 保守改库
3. 局部类型化
4. 兼容优先
