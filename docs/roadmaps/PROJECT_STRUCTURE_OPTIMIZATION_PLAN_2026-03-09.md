# 项目目录结构优化计划（2026-03-09）

> 状态：该计划对应的目录治理已基本完成。
> 当前目录结构请以 `docs/README.md`、`README.md` 以及实际仓库布局为准；本文档主要保留治理背景、分阶段约束和回滚思路。

## 1. 目标

在不改变现有业务功能的前提下，完成项目目录与运行产物治理，使仓库结构满足以下要求：

1. 源码、配置、运行数据、构建产物、临时文件各自归位。
2. 前后端对配置数据和数据库路径的约定保持单一事实来源。
3. 根目录只保留项目入口级文件，避免长期积累杂项脚本和运行文件。
4. 优化过程可分阶段落地，每一步都有明确验证方法和回滚点。

## 1.1 非目标与冻结规则

本轮优化不包含以下内容：

1. 不调整订单业务规则，包括订单解析、BOM 计算、采购单生成、打印字段和状态流转。
2. 不进行页面布局改版、视觉重设计或 CSS 体系重构。
3. 不借目录治理顺手修改组件结构、交互文案或业务字段定义。

执行约束：

1. 允许的代码改动仅限于路径收敛、配置入口统一、静态资源定位、脚本迁移、忽略规则修正和文档补齐。
2. 如因数据源统一导致订单结果发生变化，默认按回归处理，必须先证明是历史数据不一致，而不是逻辑被改写。
3. 如因遗留资源清理导致页面样式变化，默认按兼容性问题处理，只允许做最小修复，不做样式重设计。

## 2. 当前问题

### P0

1. 配置数据分散在 `data/`、`data/config/`、`public/data/` 三处，职责重叠，脚本、测试、运行时读取路径不一致。
2. SQLite 默认路径不一致，至少存在 `./data/database.sqlite`、`../../database.sqlite`、`../data/database.sqlite` 三种约定。
3. 运行产物被纳入版本库，当前已跟踪 `database.sqlite` 和 `node_modules/.package-lock.json`，会污染提交历史并增加协作噪音。

### P1

1. 根目录存在与主结构无关的脚本、素材、临时测试文件，项目入口层次不够清晰。
2. `public/` 同时承载静态资源、历史备份和配置数据，难以区分哪些是构建时资源，哪些是运行时数据。
3. `.gitignore` 与实际跟踪策略不一致，例如 `package-lock.json` 已被跟踪，但忽略规则仍将其排除。

### P2

1. 存在历史遗留入口和备份文件，例如 `.bak` 页面和 `backup_*` 目录，缺少明确的清理策略。
2. 文档已记录优化方向，但缺少一份专门面向“目录治理”的执行计划。

## 3. 目标结构

建议将仓库逐步收敛到以下结构：

```text
workspace/
├── src/                # 前端源码
├── server/             # 后端源码
├── data/
│   ├── config/         # 配置类数据唯一来源
│   └── runtime/        # 运行期数据库、缓存、导出文件
├── public/             # 纯静态资源与模板
├── scripts/            # 开发/迁移/导入脚本
├── tests/              # 自动化测试与基线数据
├── docs/               # 文档
├── temp/               # 本地调试产物（忽略）
└── package.json
```

约束：

1. `public/` 不再作为业务配置源目录。
2. `data/config/` 是映射、材料目录、采购设置等可编辑配置的唯一来源。
3. `data/runtime/` 只存放数据库、缓存、导出结果，不纳入版本库。
4. `dist/`、`temp/`、运行期数据库、截图、PDF 一律视为可重建产物。

## 4. 分阶段执行

## 阶段 A：仓库治理基线（P0，半天）

目标：先消除最影响协作的结构性噪音。

任务：

1. 修正 `.gitignore`，使其与当前仓库策略一致。
2. 停止跟踪运行产物与依赖缓存，例如 `database.sqlite`、`node_modules/.package-lock.json`。
3. 明确 `package-lock.json` 作为受控文件保留在仓库中。
4. 盘点根目录非入口文件，形成迁移清单。

验收：

1. `git ls-files` 中不再出现运行期数据库、`dist/`、`node_modules/` 内容。
2. 根目录仅保留入口文件、配置文件、必要文档与少量示例资产。

回滚点：

1. 仅涉及忽略规则和版本库跟踪范围，不改业务代码，可单独回退提交。

## 阶段 B：配置数据单一化（P0，1 天）

目标：把映射和配置数据收敛到一个事实来源。

任务：

1. 选定 `data/config/` 作为配置数据唯一来源。
2. 将 `public/data/` 中仍在使用的映射文件迁移到 `data/config/`。
3. 更新后端静态暴露策略，让前端仍可通过 `/data/...` 读取配置，但实际目录指向 `data/config/`。
4. 修改脚本和测试，统一读取 `data/config/`，去除对 `public/data/` 的耦合。
5. 为过渡期保留兼容层，但禁止新增对 `public/data/` 的依赖。

验收：

1. `rg "public/data"` 在业务代码、脚本、测试中仅剩兼容说明或迁移注释。
2. 前端配置加载、后端配置读写、测试基线全部基于统一目录。

回滚点：

1. 保留目录迁移前的文件快照。
2. 先改读取路径，再删旧目录，避免一次性切断依赖。

## 阶段 C：数据库与路径配置收敛（P0，半天）

目标：数据库路径和运行目录只有一个定义入口。

任务：

1. 保留一个数据库路径配置模块，删除重复或未使用实现。
2. 默认数据库路径改为 `data/runtime/database.sqlite`。
3. 所有依赖数据库路径的脚本、服务、测试统一走同一配置入口。
4. 明确 `DB_STORAGE` 覆盖规则，并在 README 中同步。

验收：

1. `rg "database.sqlite"` 只剩单一默认定义和测试显式覆盖。
2. 开发、测试、生产均可通过同一配置模块解析数据库位置。

回滚点：

1. 保留 `DB_STORAGE` 环境变量兼容能力。
2. 如路径迁移影响现有数据，可通过移动文件或设置环境变量回退。

## 阶段 D：根目录与遗留文件清理（P1，1 天）

目标：提升仓库入口可读性，降低新成员理解成本。

任务：

1. 将一次性脚本和数据导入脚本统一移动到 `scripts/`。
2. 将手工测试脚本迁移到 `tests/manual/` 或 `scripts/experiments/`。
3. 清理 `.bak` 页面、历史备份目录和无效静态副本。
4. 对必须保留的示例素材给出命名说明和归档位置。

验收：

1. 根目录不再出现零散测试脚本和运行中间文件。
2. `public/` 内只保留部署所需静态资源和模板。

回滚点：

1. 每类清理拆为独立提交，避免大批量删除难以追踪。

## 阶段 E：文档与门禁补齐（P1，半天）

目标：把目录规范固化，避免结构再次失控。

任务：

1. 更新 `README.md` 中的目录结构、数据库路径和数据目录说明。
2. 在工程规范文档中补充“新增文件放置规则”。
3. 增加一个简单守护测试或脚本，阻止再次跟踪 `dist/`、`node_modules/`、运行数据库。

验收：

1. 新成员可通过 README 快速理解目录职责。
2. 后续提交中若误加入运行产物，可被脚本或测试及时发现。

## 5. 实施顺序

建议按以下顺序推进：

1. 先完成阶段 A，先把版本库噪音降下来。
2. 再做阶段 B 和阶段 C，这两步决定目录治理是否真正落地。
3. 随后执行阶段 D，清理历史遗留文件。
4. 最后完成阶段 E，将规则文档化并加上守护。

## 6. 验证清单

每个阶段结束后至少执行以下检查：

1. `npm run type-check`
2. `npm test`
3. `npm run build`
4. 订单、采购、打印相关主流程 smoke 检查
5. 订单页与采购页布局样式回归检查
6. `git status --short`
7. `git ls-files | rg "^(dist|node_modules|temp)/|database\\.sqlite$"`

目标结果：

1. 构建与测试通过。
2. 仓库不再跟踪可重建产物和运行数据库。
3. 订单主流程结果与现状保持一致，除非确认是历史数据分叉导致。
4. 配置数据来源唯一且文档一致。

## 7. 风险与应对

1. 风险：测试和脚本仍依赖 `public/data/`。
   应对：先引入兼容层并批量替换引用，再删除旧目录。

2. 风险：数据库路径迁移导致本地环境读取旧库失败。
   应对：迁移阶段保留 `DB_STORAGE` 覆盖，并在 README 中给出迁移说明。

3. 风险：删除历史备份文件后失去排查依据。
   应对：将必要备份迁移到 `docs/` 或外部归档，不保留在运行目录中。

## 8. 完成标准

满足以下条件后，可认为目录优化阶段完成：

1. 目录职责可以用一句话解释清楚，且没有重复来源。
2. 根目录不再承载运行数据库、依赖缓存和零散脚本。
3. `public/`、`data/config/`、`data/runtime/` 的边界稳定。
4. 文档、代码、测试对目录约定保持一致。
