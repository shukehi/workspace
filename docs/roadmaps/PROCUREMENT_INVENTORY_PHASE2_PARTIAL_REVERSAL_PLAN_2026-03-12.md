# 采购与库存边界改造 Phase 2 子方案：部分撤销入库（2026-03-12）

## 1. 背景

当前系统已经支持：

1. 按明细、按数量执行正向入库
2. 对整条正向入库流水执行整条撤销
3. 通过反向流水回退库存与订单累计入库量

但在真实仓储作业里，经常出现以下情况：

1. 某条入库流水录了 10 个，实际只应撤回 2 个
2. 同一批到货中只有部分数量退回供应商
3. 一条原始入库流水需要分多次纠正

当前“整条撤销”无法覆盖这些场景，因此需要单独规划“部分撤销”。

## 2. 目标

本方案的目标是：

1. 允许对单条正向入库流水执行部分撤销
2. 保持库存、订单明细累计量、入库流水三者一致
3. 不破坏现有整条撤销能力
4. 保持历史可审计，禁止直接修改或删除原流水

## 3. 核心原则

1. 部分撤销仍然必须生成新的 `direction = reversal` 流水，不能改写原始流水
2. 原始正向流水可被多次部分撤销，但累计撤销量不能超过原始正向数量
3. 订单明细 `received_quantity` 永远由净流水累计结果决定
4. 库存汇总值永远由净流水累计结果决定
5. 部分撤销必须携带结构化原因 `reverse_reason`

## 4. 数据模型建议

在现有 `inventory_receipts` 基础上继续沿用：

1. `direction`
2. `source_receipt_id`
3. `reverse_reason`

无需新增主表，但建议增加一个派生概念：

1. `reversible_quantity`

计算方式：

1. 对某条 `direction = in` 的原始流水：
   - `reversible_quantity = original.quantity - sum(abs(reversal.quantity))`
2. 仅当 `reversible_quantity > 0` 时允许继续撤销

说明：

1. `reversible_quantity` 可以先不落库，按查询时计算
2. 若后续性能不够，再考虑冗余字段或物化视图

## 5. 接口建议

新增或扩展：

```http
POST /api/inventory-receipts/:id/reverse
```

请求体调整为：

```json
{
  "reversed_at": "2026-03-12T16:00:00.000Z",
  "operator": "仓管A",
  "reverse_reason": "return_to_vendor",
  "remark": "到货破损，退回 2 个",
  "quantity": 2
}
```

规则：

1. `:id` 必须指向 `direction = in` 的原始正向流水
2. `quantity > 0`
3. `quantity <= reversible_quantity`
4. 若未传 `quantity`，保持兼容现有整条撤销语义，默认撤销剩余可撤销量
5. 成功后新增一条 `direction = reversal`、`quantity = -2` 的反向流水

错误码建议：

1. `RECEIPT_NOT_FOUND`
2. `RECEIPT_REVERSE_NOT_ALLOWED`
3. `RECEIPT_ALREADY_FULLY_REVERSED`
4. `REVERSE_REASON_REQUIRED`
5. `REVERSE_QUANTITY_REQUIRED`
6. `REVERSE_QUANTITY_EXCEEDED`

## 6. 服务层规则

部分撤销成功时必须同步：

1. `Material.stock_quantity -= quantity`
2. `OrderItem.received_quantity -= quantity`
3. 若订单任一明细不再满足 `received_quantity >= ordered_quantity`，订单状态回退到 `arrived`
4. 若仍然全部满足，则订单保持 `completed`

关键点：

1. 不再使用“是否存在任何 reversal”判断原流水不可撤销
2. 改为按“剩余可撤销量是否大于 0”判断

## 7. 前端建议

库存页撤销入口应从“确认撤销整条流水”升级为：

1. 显示当前流水数量
2. 显示已撤销量
3. 显示剩余可撤销量
4. 输入本次撤销数量
5. 选择撤销原因
6. 填写补充说明
7. 提供按方向、撤销原因筛选的能力，方便聚焦撤销记录

UI 规则：

1. 若剩余可撤销量为 0，则隐藏撤销按钮
2. 默认本次撤销数量留空，不预填满
3. 可提供“全部撤销剩余量”快捷按钮

## 8. 审计与展示建议

库存页入库记录列表建议新增：

1. 原始数量
2. 已撤销量
3. 剩余可撤销量
4. 原始流水链接
5. 摘要区分“累计入库数量”和“净入库数量”
6. CSV 导出需包含方向、撤销原因、剩余可撤销
7. 列表应优先支持服务端分页，避免流水量增长后继续全量拉取
8. 导出应按已生效查询条件导出全量结果，而不是只导出当前页

详情页或抽屉建议支持：

1. 展示一条原始正向流水及其所有撤销子流水
2. 展示净结果

## 9. 实施顺序建议

当前进展：

1. `reverseReceipt()` 已支持数量参数
2. 库存页撤销弹窗已支持部分撤销数量输入
3. 列表已展示“剩余可撤销量”
4. 库存页已新增“入库撤销轨迹”详情抽屉，支持查看原始流水及其撤销子流水，并可直接跳转采购单
5. 库存页筛选与分页已改为服务端驱动，避免当前页本地过滤导致的口径偏差
6. 库存页已补充 `pageSize` 切换，且导出会按当前已生效筛选条件拉取全量结果
7. 轨迹抽屉在分页场景下会单独拉取完整订单流水，避免当前页缺少原始记录时无法审计

后续建议顺序：

1. 补独立详情页或抽屉，支持更完整的审计展示
2. 为撤销原因增加筛选与统计
3. 再考虑是否恢复批量入库/批量撤销

## 10. 明确暂不做

1. 不做跨多条正向流水的合并撤销
2. 不做自动拆分原始入库流水
3. 不做撤销审批流
