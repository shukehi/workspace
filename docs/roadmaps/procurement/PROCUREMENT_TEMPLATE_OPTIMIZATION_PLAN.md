# 采购订单录入模板优化计划

## 背景

当前采购订单录入窗口暴露了 6 个“类别”选项：

- 包装
- 锁芯
- 锁具
- 拉手
- 锁叉
- 五金/配件

但从实际代码结构看，这 6 个选项里只有一部分代表真正独立的录入模板，另外几项只是业务类别不同、录入结构却基本相同。当前把它们全部作为“录入时手动选择的类别”，会带来几个问题：

1. 用户认知负担高，不容易判断该选哪个。
2. 中途切换类别会重建明细结构，存在误清空已录内容的风险。
3. `category` 同时承担“录入模板”和“业务归类”两种职责，语义混杂。
4. 前后端校验、打印、数量逻辑都依赖类别，后续扩展成本高。

本计划目标是将“录入模板”和“业务类别”拆开，降低录入复杂度，同时保证历史数据、筛选统计和打印链路稳定。

## 目标

将当前 6 个录入类别收敛为 4 个录入模板：

1. 包装
2. 锁芯
3. 双开门配件
4. 通用配件

其中：

- `包装` 保留独立模板
- `锁芯` 保留独立模板
- `锁具 + 拉手` 合并为 `双开门配件`
- `锁叉 + 五金/配件` 合并为 `通用配件`

同时保留现有 `category` 作为业务归类字段，避免影响历史订单、列表筛选、统计与报表。

## 模板收敛依据

### 1. 必须独立保留的模板

#### 包装

包装模板与其他类别差异明显：

- 独有 `门边` 字段
- 使用左右数量列
- 有专属表头名称逻辑
- 有默认包装供应商逻辑

因此必须保留独立模板。

#### 锁芯

锁芯模板与其他类别的主要差异在于：

- 使用 `偏心` 字段
- 明细结构与普通规格字段不同
- 校验逻辑单独分支

因此也应保留独立模板。

### 2. 建议合并的模板

#### 锁具 + 拉手 -> 双开门配件

这两类当前实际结构基本一致：

- 列结构一致：产品名称、规格、左数量、右数量、单位、备注
- 都使用左右数量逻辑
- 校验规则没有本质区别

因此没有必要在录入层面拆成两个模板。

#### 锁叉 + 五金/配件 -> 通用配件

这两类都使用单数量模式，不走左右数量。差异主要体现在显示名称和是否带单位字段上。录入层面可以统一为一个“通用配件”模板，再通过业务类别保留归类差异。

通用配件模板在第一阶段直接定稿为统一字段集合：

- 产品名称
- 规格
- 数量
- 单位
- 备注

具体规则：

1. 保留 `unit` 字段
2. 默认单位为 `个`
3. 校验口径为：产品名称必填、规格必填、数量大于 0、单位非强必填
4. 新单打印按统一后的通用配件列结构渲染
5. 历史 `锁叉` / `五金配件` 单据继续按旧 `category` 兼容推断

## 设计原则

### 1. 模板负责录入结构

模板决定：

- 表格列结构
- 明细空行结构
- 数量模式
- 默认值
- 校验规则

### 2. 类别负责业务归档

类别继续用于：

- 列表筛选
- 统计汇总
- 标签显示
- 历史兼容

### 3. 进入弹窗前确定模板

模板应在“创建采购订单”入口处决定，而不是在弹窗里作为普通字段频繁切换。

### 4. 历史兼容优先

旧订单应继续保持可打开、可编辑、可打印，不要求一次性重写历史 `category`。

## 数据模型建议

建议新增模板字段，而不是直接重定义 `category`。

### 新增字段

建议在订单元数据中新增：

`metadata.template_type`

建议枚举值：

- `packaging`
- `cylinder`
- `double-door-accessory`
- `general-accessory`

生命周期说明：

1. 第一阶段把 `template_type` 放在 `metadata` 中，目标是最小化改动范围
2. 第二阶段继续允许它驱动录入、校验和打印，但不把它作为高频查询条件
3. 若后续需要按模板筛选、统计、导出或排错，再评估升格为顶层字段并补索引

这意味着 `metadata.template_type` 是过渡但可运行的方案，不是最终数据建模终点

### 旧类别到新模板的映射

- `包装 -> packaging`
- `锁芯 -> cylinder`
- `锁具 -> double-door-accessory`
- `拉手 -> double-door-accessory`
- `锁叉 -> general-accessory`
- `五金/配件 -> general-accessory`

### 兼容策略

1. 新建订单时，前端显式写入 `metadata.template_type`
2. 后端保存时兜底补全 `metadata.template_type`
3. 历史订单无该字段时，根据 `category` 推断模板
4. 列表、统计与筛选继续使用 `category`

这样可以避免第一阶段就大规模改动业务统计逻辑。

## 前端改造方案

### 1. 创建入口改造

将“新建采购单”入口改为模板入口：

- 新建包装采购单
- 新建锁芯采购单
- 新建双开门配件采购单
- 新建通用配件采购单

### 2. 录入弹窗改造

录入弹窗内：

- 模板改为只读显示或弱化展示
- 不再鼓励中途切换
- 如允许切换模板，必须弹出明确确认

建议提示文案：

`更换模板会重置当前明细内容，是否继续？`

### 3. 类别显示策略

为保证新单 `orders.category` 落库稳定，第一阶段不能只选模板不选类别。推荐策略是：

1. 先选模板
2. 若模板只对应一个业务类别，则自动写入该类别
3. 若模板对应多个业务类别，则补一个轻量业务类别单选

明确规则：

- `包装` 模板固定写入 `包装`
- `锁芯` 模板固定写入 `锁芯`
- `双开门配件` 模板要求二选一：`锁具 / 拉手`
- `通用配件` 模板要求二选一：`锁叉 / 五金/配件`

这样既能把录入模板收敛到 4 个，也不会破坏现有列表筛选、统计和标签语义。

## 后端改造方案

### 1. 校验层改造

将当前“按 category 校验”逐步改为“按 template_type 校验”：

- 明细字段要求
- 数量字段处理
- 空白行过滤
- 有效明细判断

### 2. 保存层兼容

保存时：

- 若存在 `metadata.template_type`，优先按模板处理
- 若不存在，则回退按 `category` 推断

### 3. 查询层保持稳定

列表查询、聚合统计、状态筛选暂不改为按模板聚合，减少本次 blast radius。

## 打印与预览方案

打印预览应逐步切换到“按模板渲染”的模式。

建议策略：

1. 新订单优先使用 `template_type`
2. 历史订单继续按 `category` 推断模板
3. PDF 文件名、标题显示仍使用业务类别或中文标签，避免用户感知混乱

## 风险与控制

### 风险 1：模板与类别双概念并存导致混乱

控制方式：

- 第一阶段只在内部逻辑引入模板概念
- UI 优先展示模板，不暴露过多技术字段

### 风险 2：历史数据行为变化

控制方式：

- 保留 `category`
- 采用读取时推断模板的兼容模式
- 不强制一次性迁移历史订单

### 风险 3：打印链路回归

控制方式：

- 新老单据双路径测试
- 在模板切换阶段重点补打印回归测试

## 建议结论

本次优化不建议直接“删掉类别”，而应采用以下策略：

1. 新增模板层
2. 录入按模板
3. 归档按类别
4. 先收敛到 4 个模板
5. 保持历史兼容

这是在当前代码结构下风险最低、收益最高的改法。
