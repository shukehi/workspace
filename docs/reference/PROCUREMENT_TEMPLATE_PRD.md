# 采购订单录入模板优化 PRD

## 1. 背景

当前采购订单录入流程将“类别”直接作为“录入模板”使用。系统当前暴露 6 个类别：

- 包装
- 锁芯
- 锁具
- 拉手
- 锁叉
- 五金/配件

但从现有实现看，这 6 个类别并不都对应真正独立的录入结构。其中一部分只是业务归类不同，录入字段、数量逻辑与校验规则却高度相似。

这导致当前录入体验存在以下问题：

1. 用户需要先理解类别差异，录入门槛高。
2. 弹窗内切换类别会重建明细结构，存在误清空风险。
3. `category` 同时承担“录入模板”和“业务归类”两种职责，逻辑耦合严重。
4. 前后端校验、打印和数量计算都被类别驱动，导致扩展成本持续上升。

## 2. 问题定义

### 2.1 用户侧问题

- 录单员不知道“该选哪个类别”。
- 类别选择对录入结构影响太大，但界面没有充分解释。
- 一旦切错类别，明细内容容易丢失。

### 2.2 系统侧问题

- 明细 schema、数量逻辑、默认值、校验都绑定在类别上。
- 同结构模板被拆散，导致重复逻辑增多。
- 历史数据、查询统计与录入模型混在一个字段里，后续演进困难。

## 3. 产品目标

将采购订单录入从“按类别录单”调整为“按模板录单”，实现以下目标：

1. 降低录入门槛，减少用户选择成本。
2. 降低录入中途误切换模板导致的数据丢失风险。
3. 将录入结构与业务归类解耦。
4. 在不破坏历史数据、筛选统计和打印链路的前提下，逐步完成模板收敛。

## 4. 非目标

以下内容不在本次优化第一阶段范围内：

1. 不重构采购订单列表的筛选/统计逻辑。
2. 不强制迁移所有历史订单数据。
3. 不在第一阶段引入新的报表维度。
4. 不一次性删除现有 `category` 字段。

## 5. 目标方案

### 5.1 模板收敛目标

将现有 6 个录入类别收敛为 4 个录入模板：

1. 包装
2. 锁芯
3. 双开门配件
4. 通用配件

### 5.2 模板映射关系

| 现有类别 | 新模板 |
| --- | --- |
| 包装 | packaging |
| 锁芯 | cylinder |
| 锁具 | double-door-accessory |
| 拉手 | double-door-accessory |
| 锁叉 | general-accessory |
| 五金/配件 | general-accessory |

## 6. 为什么这样拆

### 6.1 保留独立模板

#### 包装

包装模板必须保留独立，原因：

- 有独有字段 `门边`
- 使用左右数量模式
- 有专属默认供应商逻辑
- 有包装专属表头名称逻辑

#### 锁芯

锁芯模板必须保留独立，原因：

- 有独有字段 `偏心`
- 明细结构与常规规格字段不同
- 校验逻辑存在独立分支

### 6.2 合并模板

#### 锁具 + 拉手

合并原因：

- 列结构基本一致
- 都使用左右数量
- 校验逻辑无本质差异

建议统一为 `双开门配件` 模板。

#### 锁叉 + 五金/配件

合并原因：

- 都使用单数量模式
- 都属于普通配件录入结构
- 差异主要体现在标签命名，而非录入结构

建议统一为 `通用配件` 模板。

#### 通用配件模板字段收敛规则

`通用配件` 模板在第一阶段直接定为统一 schema，避免第二阶段反复返工。最终字段定义为：

- 产品名称
- 规格
- 数量
- 单位
- 备注

配套规则如下：

1. 保留 `unit` 字段  
原因是 `锁叉` 现有模板已依赖单位；对 `五金/配件` 来说，多一个单位字段的代价低于后续补字段的代价。

2. 默认单位为 `个`  
若后续物料主数据可提供更准确单位，再由物料映射覆盖。

3. 校验口径统一为：产品名称必填、规格必填、数量大于 0、单位非强必填  
这样既能保持结构完整，也不会压坏当前 `五金/配件` 的录入习惯。

4. 新单打印按统一后的 `通用配件` 列结构渲染  
历史 `锁叉` / `五金配件` 单据继续按旧 `category` 兼容推断模板，避免老单打印布局突变。

## 7. 产品设计原则

### 7.1 模板负责录入结构

模板决定：

- 表格列定义
- 明细空行结构
- 数量计算模式
- 默认值
- 校验规则
- 打印结构

### 7.2 类别负责业务归档

类别继续用于：

- 列表筛选
- 分类统计
- 标签显示
- 历史兼容

### 7.3 模板在进入弹窗前确定

模板不应作为用户在录入过程中频繁切换的普通字段，而应在创建入口处基本确定。

## 8. 数据模型方案

### 8.1 新增字段

建议新增：

`metadata.template_type`

建议枚举值：

- `packaging`
- `cylinder`
- `double-door-accessory`
- `general-accessory`

### 8.2 字段职责拆分

#### `category`

继续承担：

- 业务归类
- 历史兼容
- 查询/统计维度

#### `metadata.template_type`

承担：

- 录入模板选择
- schema 映射
- 校验逻辑分支
- 打印结构选择

#### 生命周期与治理边界

`metadata.template_type` 在本方案中定义为 `过渡但可稳定运行的字段`，不是最终数据建模终点。

边界定义如下：

1. 第一阶段  
放在 `metadata` 中，目标是以最小 blast radius 引入模板层，不改动现有列表筛选、聚合统计和查询结构。

2. 第二阶段  
允许继续按 `metadata.template_type` 驱动录入、校验和打印，但不承诺基于该字段做高频查询或索引优化。

3. 第三阶段评估点  
若后续出现以下任一需求，则评估将 `template_type` 升格为顶层字段：
- 按模板筛选订单
- 按模板做聚合统计
- 按模板导出或对账
- 高频排查线上问题需要按模板查询

4. 升格原则  
只有当模板维度进入稳定查询面时，才新增顶层列或独立索引；在此之前，`metadata.template_type` 只承担应用层兼容职责。

### 8.3 兼容策略

1. 新建订单时显式写入 `metadata.template_type`
2. 后端保存时兜底补齐该字段
3. 旧订单若无该字段，则按 `category` 推断
4. 列表与统计继续按 `category` 工作

## 9. 交互方案

### 9.1 创建入口

将“新建采购单”改造为模板入口：

- 新建包装采购单
- 新建锁芯采购单
- 新建双开门配件采购单
- 新建通用配件采购单

### 9.2 录入弹窗

录入弹窗内：

- 模板作为只读信息展示
- 不再默认提供“普通类别下拉切换”
- 若支持模板切换，必须增加强确认

建议提示文案：

`更换模板会重置当前明细内容，是否继续？`

### 9.3 用户感知

第一阶段不建议把“模板”和“类别”以同等权重暴露给用户，但新单必须有明确的 `category` 落库规则，否则会直接影响列表筛选、统计和标签语义。

推荐交互：

1. 用户先选择模板
2. 若模板对应多个业务类别，再展示一个轻量业务类别单选

落库规则明确如下：

- 选择 `包装` 模板时，`category` 固定写入 `包装`
- 选择 `锁芯` 模板时，`category` 固定写入 `锁芯`
- 选择 `双开门配件` 模板时，必须二选一：`锁具 / 拉手`
- 选择 `通用配件` 模板时，必须二选一：`锁叉 / 五金/配件`

这样可以同时满足：

- 录入模板数收敛到 4 个
- `orders.category` 仍保持原有业务粒度
- 列表筛选、统计、打印标签和历史报表语义不失真

## 10. 系统方案

### 10.1 前端

需要改造的模块包括：

- 录入弹窗
- 明细表 schema
- 草稿初始化
- 模板切换逻辑
- 模板级校验
- 打印预览构建

### 10.2 后端

需要改造的模块包括：

- 手动单创建校验
- 手动单更新校验
- 明细清洗逻辑
- 打印/返回数据映射
- 模板兼容映射

### 10.3 历史订单

历史订单不强制迁移，只要求：

- 能正常读取
- 能正常编辑
- 能正常打印

## 12. 验收标准

### 12.1 录入

1. 四个模板都能正确初始化草稿。
2. 模板切换时会有明确保护。
3. 包装模板仍会保留默认供应商和专属表头。
4. 锁芯模板仍能正确处理偏心字段。
5. 双开门配件模板左右数量计算正确。
6. 通用配件模板单数量校验正确。
7. 选择 `双开门配件` 模板时，必须出现 `锁具 / 拉手` 业务类别选择。
8. 选择 `通用配件` 模板时，必须出现 `锁叉 / 五金/配件` 业务类别选择。
9. 选择 `包装` 或 `锁芯` 模板时，不出现额外业务类别选择。
10. 从采购页点击 `双开门配件` 或 `通用配件` 入口进入时，业务类别不得被默认选中，必须保持“请选择业务类别”。

### 12.2 保存

1. 新建订单会写入 `metadata.template_type`。
2. 后端会补齐缺失模板字段。
3. 手动单创建与更新校验逻辑不回退。
4. 空白明细过滤继续有效。
5. `双开门配件` 模板创建的新单会按用户选择正确落库为 `锁具` 或 `拉手`。
6. `通用配件` 模板创建的新单会按用户选择正确落库为 `锁叉` 或 `五金/配件`。

### 12.3 历史兼容

1. 历史订单能正常打开。
2. 历史订单能正常编辑。
3. 历史订单能正常打印。
4. 列表筛选和统计不回退。
5. 新增模板订单进入列表后，分类筛选和分类统计仍按原 `category` 语义表现正确。

### 12.4 打印

1. 新模板生成的打印结构正确。
2. PDF 文件名与标题保持可读。
3. 新老单据打印行为稳定。
4. `拉手` 在共享双开门模板下仍保持 `付` 作为默认单位。
5. `五金/配件` 在共享通用配件模板下仍保持原业务类别排序，不误用锁叉排序。
6. 无类别旧单不会被静默打印成包装单。

## 13. 风险与应对

### 风险 1：模板与类别双概念并存

应对：

- 第一阶段只在内部逻辑引入模板概念
- UI 优先展示模板，不增加用户认知负担

### 风险 2：历史单据兼容异常

应对：

- 历史数据采用读取时推断模板
- 保留原 `category`
- 为旧单据编辑和打印补专项回归测试

### 风险 3：打印链路回归

应对：

- 模板切换阶段同步补打印测试
- 新老单据双路径验证

## 14. 成功标准

本次优化成功的标志是：

1. 用户新建采购单时，不再需要理解 6 套录入模板。
2. 录入窗口模板结构更稳定，中途误切换风险显著下降。
3. 前后端录入逻辑不再高度依赖 `category`。
4. 历史订单、列表筛选、统计和打印均保持稳定。

截至 2026-03-29：

- 第 3、4 条已基本达成
- 第 1、2 条在第三阶段已大部分完成，剩余主要是页面级自动化验证与少量交互保护增强

## 15. 结论

本次采购订单录入优化的最佳路径不是直接删除类别，而是：

1. 保留 `category` 作为业务归档字段
2. 新增 `template_type` 作为录入模板字段
3. 将 6 个录入模板收敛为 4 个
4. 通过分阶段实施完成从“按类别录单”到“按模板录单”的切换

这是当前代码结构下风险最低、收益最高的实施方案。
