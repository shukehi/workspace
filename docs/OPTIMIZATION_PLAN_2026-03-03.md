# 项目优化计划（2026-03-03）

## 1. 目标与范围

### 1.1 总目标
在不影响现有业务功能的前提下，完成前后端契约统一、数据链路稳定化、技术债收敛与基础测试建设，使项目从“可运行”提升到“可持续迭代”。

### 1.2 本次计划覆盖
- 前端 `src`（Vue + Pinia + TS）
- 后端 `server`（Express + Sequelize + SQLite）
- 配置与遗留逻辑（`src/lib/legacy`、`public/js`）
- 文档与工程规范

### 1.3 不覆盖（本轮）
- 大规模 UI 重设计
- 数据库替换（如 SQLite -> MySQL）
- ERP 外部接口协议变更

---

## 2. 现状问题（摘要）

### P0（立即处理）
1. 接口路径不一致：前端调用 `/api/inventory`、`/api/formulas`，后端未完整提供对应路由。
2. Mock 与真实 API 混用：部分模块走 `axiosInstance`，部分模块走原生 `axios`，开发与联调数据源不一致。

### P1（短期处理）
1. 类型契约偏差：前端 `Order.id` 为 `string`，后端模型为 `INTEGER`。
2. 文档严重过期：README 与实际技术栈/启动方式/目录不匹配。

### P2（中期处理）
1. 旧新代码并存：`src/lib/legacy` 与 `public/js` 存在重复逻辑，长期维护成本高。
2. 自动化测试缺失：回归保障不足。

---

## 3. 优化原则

1. 先稳链路，再做重构。
2. 先统一契约，再追求抽象优雅。
3. 每一阶段必须有可验证的验收结果。
4. 优化过程保持可回滚，避免一次性大改。

---

## 4. 分阶段执行计划

## 阶段 A：链路修复与契约统一（1-2 天）

### A1. API 访问层统一
- 任务：所有前端请求统一使用 `@/lib/api`，禁止直接 `axios`。
- 输出：
  - 替换 `useProcurementStore.ts`、`useInventoryStore.ts` 中直连请求。
  - 新增约束文档：前端网络请求规范。
- 验收：全项目 `src` 内不再出现 `import axios from 'axios'`（除 `lib/api.ts`）。

### A2. 补齐/对齐后端接口
- 任务：
  - 增加库存接口（至少 `GET /api/inventory`，如需可补 `PUT /api/inventory/:id`）。
  - 统一配方接口路径：前端改为 `/api/config/formulas`，或后端提供 `/api/formulas` 兼容层。
- 验收：Dashboard、Inventory、Statistics 页面在真实后端下无 404。

### A3. Mock 开关清晰化
- 任务：仅在 `VITE_USE_MOCK=true` 时启用 Mock。
- 验收：
  - `VITE_USE_MOCK=true`：核心页面数据均来自 Mock。
  - `VITE_USE_MOCK=false`：核心页面全部走真实后端。

---

## 阶段 B：类型与数据一致性（1-2 天）

### B1. 统一 ID 类型
- 任务：前后端统一 `Order.id`、`OrderItem.id` 类型（建议统一 `number`）。
- 输出：
  - 更新 `src/types/*.ts`。
  - 修复比较/筛选/批量操作中的类型隐患。
- 验收：TypeScript 无类型回退（无 `@ts-ignore` 新增），订单增删改查与批量操作稳定。

### B2. API 响应结构规范化
- 任务：明确 `api.ts` 的返回约定（直接 payload 或 `{ success, data }`），并全仓一致。
- 验收：所有 store 的请求处理逻辑一致，无“某些接口多一层 data”问题。

---

## 阶段 C：遗留逻辑收敛（3-5 天）

### C1. Legacy 边界封装
- 任务：为 `src/lib/legacy/*` 增加单一适配层（facade），业务层不直接依赖 legacy 函数。
- 验收：业务 store 不再直接 import 多个 legacy 文件。

### C2. 旧代码去冗余计划
- 任务：梳理 `public/js` 中已被 `src` 替代的模块，建立“可删除清单”。
- 验收：给出分批删除表（文件名、依赖、风险、回滚点）。

---

## 阶段 D：测试与质量门禁（2-3 天）

### D1. 最小回归测试集
- 范围：
  - 后端：订单 CRUD、分类筛选、配置接口。
  - 前端：采购页加载/筛选/状态更新关键流程。
- 目标：覆盖关键业务链路，而非追求覆盖率数字。
- 验收：CI 或本地 `npm test` 可稳定执行，核心用例通过。

### D2. 静态检查与脚本化
- 任务：补充基础 lint/type-check 脚本，统一构建前检查。
- 验收：PR 合并前至少执行 type-check + build + smoke tests。

---

## 阶段 E：文档与协作规范（1 天）

### E1. README 重写（与现状一致）
- 更新内容：技术栈、启动方式（前后端）、目录结构、主要 API、Mock 开关。

### E2. 开发约定文档
- 内容：
  - API 路径命名规范
  - 前端请求规范（统一入口）
  - 类型变更流程
  - 迁移策略（legacy -> new）

- 验收：新成员可按文档在 30 分钟内完成本地运行与基本调试。

---

## 5. 里程碑与交付物

### M1（第 2 天）
- 链路可用：所有主页面真实后端可访问，无关键 404。
- 交付：接口对齐 PR + API 访问统一 PR。

### M2（第 4 天）
- 契约稳定：类型统一、批量操作稳定。
- 交付：类型修复 PR + 数据契约说明文档。

### M3（第 8 天）
- 技术债收敛：legacy 通过 facade 管理，旧代码去冗余清单完成。
- 交付：重构 PR + 去除计划文档。

### M4（第 10 天）
- 质量闭环：关键回归测试可执行，文档更新到位。
- 交付：测试 PR + README/开发规范文档。

---

## 6. 风险与应对

1. 风险：ERP 返回结构不稳定导致前端解析失败。
- 应对：增加响应适配层 + 示例快照 + 容错日志。

2. 风险：迁移 legacy 触发隐性业务回归。
- 应对：先建立 facade，再替换调用点，最后删旧代码。

3. 风险：接口改动影响已在开发中的前端分支。
- 应对：提供兼容层（别名路由）与变更公告，设置过渡期。

---

## 7. 验收指标（量化）

1. 构建与类型检查：`npm run build` 连续 5 次通过。
2. 主流程可用性：采购、库存、统计、来源分析页面关键流程全部可操作。
3. 契约一致性：核心实体（Order/OrderItem/Inventory）类型与数据库一致。
4. 测试保障：至少覆盖订单 CRUD + 分类筛选 + 配置读取保存的自动化用例。
5. 文档一致性：README 与当前代码结构、命令、接口保持一致。

---

## 8. 建议执行顺序（可直接开工）

1. 先做阶段 A（接口+请求层统一）。
2. 再做阶段 B（类型与响应结构统一）。
3. 随后做阶段 D（先补最小测试，防止后续重构失控）。
4. 最后并行推进阶段 C/E（技术债与文档）。
